Problema 1: Concurrencia — ¿Cómo evitamos conflictos de cupo?

⚠️ El problema
50 estudiantes presionan "Inscribirse" al mismo tiempo. Solo queda 1 cupo. Sin protección, los 50 podrían quedar inscritos — violando la regla de negocio.
Escenario sin protección: T1 (usuario A): READ cupo=1 → cupo>0 ✓ T2 (usuario B): READ cupo=1 → cupo>0 ✓ T1: INSERT inscripcion → UPDATE cupo=0 T2: INSERT inscripcion → UPDATE cupo=-1 ❌ → CUPO NEGATIVO Con SELECT FOR UPDATE: T1: SELECT cupo FOR UPDATE → LOCK ✓ T2: SELECT cupo FOR UPDATE → ESPERA T1: INSERT + UPDATE cupo=0 → COMMIT → LOCK liberado T2: READ cupo=0 → SinCuposException ✓ → Nunca llega al INSERT
Mecanismos aplicados:
SELECT FOR UPDATE (ADR-07)
Bloqueo pesimista sobre la fila del evento · Garantiza atomicidad
Idempotency Key (ADR-09, RF-20b)
UUID único por intento · Reintentos del cliente no duplican inscripciones
Circuit Breaker (ADR-18, Resilience4j)
Fallo de payment-service no bloquea inscription-service indefinidamente
Outbox + DLQ (ADR-11, ADR-019)
Mensajes de pago no se pierden aunque el broker caiga momentáneamente
✅ Resultado: 500 VU simultáneos · 0 cupos duplicados · 0 inconsistencias

Problema 2: Escalabilidad — ¿Cómo soportamos más carga?

🎯 El desafío
Un congreso con 500 inscritos potenciales accede al catálogo en segundos tras el anuncio. Sin preparación, el sistema colapsa.
Cómo cada capa escala:
CloudFront CDN → Archivos estáticos servidos desde edge. Sin carga al origen.
Redis Cache-Aside (ADR-05) → Catálogo en caché 5 min. 95% de lecturas sin tocar PostgreSQL.
Microservicios independientes → event-service escala x3 sin afectar inscription-service.
JWT stateless → Sin sesiones en servidor. Cualquier instancia atiende cualquier request.
RabbitMQ AMQP → Picos de confirmación de pago procesados en cola, no en request-path.

Factory Method + Adapter — Pasarela de pagos

Factory Method (GoF Creacional)

<<interface>> PasarelaPagoFactory └─ crearPasarela(): PasarelaPagoPort ▲ │ implements DefaultPasarelaPagoFactory switch (provider) "mercadopago" → MercadoPagoAdapter default → SimuladorPasarelaAdapter <<interface>> PasarelaPagoPort ← Puerto hexagonal └─ crearPreferencia(...) └─ confirmarPago(...) ▲ ▲ MercadoPagoAdapter SimuladorPasarelaAdapter
OCP aplicado: Añadir PayU = nueva clase + 1 rama en switch. Sin tocar CrearPreferenciaService.

Adapter (GoF Estructural)

Puerto dominio → Adaptador → Infraestructura EventoCachePort └─ RedisEventoCacheAdapter → RedisTemplate EventoServicePort (Feign) └─ EventoServiceAdapter → EventoServiceFeignClient PaymentServicePort └─ PaymentServiceAdapter → HTTP (Feign + CB) PasarelaPagoPort └─ MercadoPagoAdapter → SDK MercadoPago └─ SimuladorAdapter → HTTP interno
Principio: El dominio define el contrato (Port). La infraestructura lo implementa (Adapter). Nunca al revés.
